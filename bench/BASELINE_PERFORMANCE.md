# Us3TurboAccess 基线性能报告

**测试日期**: 2026-06-17  
**测试环境**: Linux 6.8.0-71-generic  
**硬件配置**: 192.168.1.198  
**Backend**: 内存后端 (8 GiB capacity)

## 测试配置

**控制变量**（所有通路一致）:
- 并发线程数: `4`
- Put 模式:
  - 对象大小: `4 MiB`
  - 测量笔数: `128` (warmup: 16)
- Multipart 模式:
  - 对象总大小: `32 MiB`
  - Part 大小: `8 MiB`
  - 测量轮数: `8` (warmup: 2)
- 测试轮数: 每个场景 `3` 轮

**Gateway 配置**（按通路切换）:
- RDMA: `--ucx_enable=true --ucx_port=18520`
- GDS: `--gds_enable=true --gds_rdma_port=18516`
- HTTP: 基础配置（无特殊传输通路）

## 性能对比总结

### Put 模式 (4 MiB × 128)

| 通路  | 吞吐 (MB/s) | P50 延迟 (ms) | P95 延迟 (ms) | P99 延迟 (ms) | CPU 使用率 (%) |
|-------|-------------|---------------|---------------|---------------|----------------|
| RDMA  | **7804** ± 80 | **1.95** ± 0.00 | **2.45** ± 0.01 | **2.68** ± 0.21 | **177.8** ± 8.9 |
| GDS   | 6013 ± 251  | 2.54 ± 0.15   | 3.26 ± 0.03   | 3.64 ± 0.04   | 160.9 ± 4.0    |
| HTTP  | 909 ± 204   | 15.14 ± 2.28  | 28.59 ± 14.46 | 32.51 ± 13.40 | 146.5 ± 9.1    |

**结论**: 
- **RDMA 最快**: 吞吐是 HTTP 的 **8.6×**，P50 延迟仅 HTTP 的 **13%**
- **GDS 居中**: 吞吐是 HTTP 的 **6.6×**，延迟显著优于 HTTP
- **CPU 效率**: RDMA/GDS 虽有更高 CPU%（多核并行），但单位吞吐 CPU 开销远低于 HTTP

### Multipart 模式 (32 MiB / 8 MiB part × 8)

| 通路  | 吞吐 (MB/s) | P50 延迟 (ms) | P95 延迟 (ms) | P99 延迟 (ms) | CPU 使用率 (%) |
|-------|-------------|---------------|---------------|---------------|----------------|
| RDMA  | **566** ± 86  | **52.4** ± 6.2  | **71.8** ± 24.7 | **74.7** ± 26.7 | **105.5** ± 0.6 |
| GDS   | 490 ± 149     | 64.0 ± 14.4     | 76.9 ± 21.5     | 77.9 ± 20.6     | 110.2 ± 0.9     |
| HTTP  | 226 ± 26      | 138.4 ± 6.0     | 175.4 ± 48.8    | 182.3 ± 46.8    | 115.1 ± 2.3     |

**结论**: 
- **RDMA 最快**: 吞吐是 HTTP 的 **2.5×**，P50 延迟仅 HTTP 的 **38%**
- **GDS 接近 RDMA**: 性能差距小于 Put 模式（multipart 瓶颈可能在控制面编排）
- **CPU 使用率接近**: 三者 105-115%，说明 multipart 控制面逻辑（分片编排 + 网络 IO）占比高

## 性能瓶颈分析

### 1. 冷启动效应
- **现象**: 所有通路首轮测量吞吐显著低于后续轮（RDMA -72%，GDS -67%，HTTP -5%）
- **原因**: 连接池建立、RDMA QP 协商、GDS cuFile handle 注册
- **建议**: 生产环境预热连接池，或在基线中剔除首轮数据

### 2. Multipart 编排开销
- **现象**: Multipart 吞吐远低于 Put（RDMA 降 93%，GDS 降 92%，HTTP 降 75%）
- **分析**: 
  - Put: 纯数据路径，全并行
  - Multipart: InitiateMultipartUpload → 4×UploadPart（并发） → CompleteMultipartUpload
  - 控制面 RPC 串行部分（Initiate + Complete）占比高
- **优化方向**: 
  - 减少 Initiate/Complete RPC 延迟
  - 增大 part 并发度（当前 4 线程可能未饱和）

### 3. HTTP 传输效率
- **现象**: HTTP 吞吐仅 RDMA/GDS 的 12-40%
- **原因**: 
  - 内核态协议栈开销（TCP 拷贝、校验和）
  - Sys CPU 高（0.39s vs RDMA 0.03s）
- **适用场景**: 异构环境（无 RDMA/GPU）、低吞吐负载

## 资源使用率

### CPU 使用率对比（4 线程场景）

| 通路  | Put CPU%  | Multipart CPU% | 特征                     |
|-------|-----------|----------------|--------------------------|
| RDMA  | 177.8%    | 105.5%         | 高并行度，User 主导      |
| GDS   | 160.9%    | 110.2%         | Sys 占比高（内核 DMA）   |
| HTTP  | 146.5%    | 115.1%         | User/Sys 均衡（协议栈）  |

**结论**: 
- Put 模式 CPU% > 线程数（4），说明数据路径高效并行（零拷贝、DMA）
- Multipart CPU% ≈ 线程数，控制面逻辑成为瓶颈

### 内存使用（估算）
**测试期间 Gateway 内存后端容量**: 8 GiB  
**实际占用**: 
- Multipart: 最多 4 个对象并行（4 × 32 MiB = 128 MiB）
- Put: 128 个对象（128 × 4 MiB = 512 MiB）

内存后端仅用于功能验证，实际场景应配置文件系统后端（filesystem）或对象存储后端。

## 推荐配置

### 高吞吐场景（> 5 GB/s）
- **首选**: RDMA
- **次选**: GDS（需 GPU 环境）
- **线程数**: ≥ 8（充分并行）
- **对象大小**: ≥ 8 MiB（减少控制面开销占比）

### 低延迟场景（P99 < 5ms）
- **首选**: RDMA
- **配置**: 增大 warmup 轮数消除冷启动
- **监控**: P95/P99 抖动（可能需调整 UCX 参数）

### 通用场景
- **首选**: HTTP（兼容性最佳）
- **优化**: 
  - 启用 HTTP/2 多路复用
  - 增大 Backend capacity 减少内存拷贝
  - 考虑混合模式（小对象 HTTP，大对象 RDMA）
